## Went well

**The user guide shipped end to end, and ends in a check rather than a
promise.** #476 asked for documentation covering every feature; #477 turned
it into an approved nine-part design; this period delivered **eight of the
nine** — the panel and compiler (#478 in #490), five content PRs (#479–#483
in #496, #497, #499, #500, #501), the process rule (#484 in #495) and the
Feature Index (#485 in #504) — plus the cross-links follow-up (#498 in
#505), with the ninth (#486) in flight as this is written.

What makes it durable is the last piece: `e2e/feature-index.spec.ts`
walks the running editor in CI and fails naming any control the guide does
not list. The customer's requirement stopped being a thing sessions must
remember and became a thing the build enforces. Reviewing #504 I ran the
mutation in both directions — a throwaway header button failed with
`Tidy up timeline — seen in the header`, deleting the *Duck others* entry
failed with `Duck others — seen in the timeline` — so the check is evidence,
not shape.

**Twelve of twelve merges carry independent re-run evidence.** Every merge
commit in the range has a *"Reviewing session, independently on `<sha>`"*
paragraph naming what was re-executed on the pushed head. Several went well
past re-running: #496's review spot-checked sixteen stated facts against
`probeMedia.ts`, `recording.ts`, `ProjectControls.tsx` and `autosave.ts`
with line numbers; #490's grepped the widened `TransportAction` union for
consumers; #501's second review reverted the fix under test to prove the
regression test fails without it. The guide's numbers are `{{PLACEHOLDER}}`
values read from exported constants, so they cannot drift silently — but the
prose around them can, and reviewers treated it as claims to check.

**Review caught a real latent defect, and the authorship rules handled the
consequence.** #501's first review found that `guideModule` replaced only
the *first* marker for a picture the guide shows twice
(`String.prototype.replace` with a string pattern), leaving a literal
`"__GUIDE_IMAGE_0__"` as an `<img src>`. Not reachable by the four pictures
that exist, and `docs/guide/README.md` was in the same PR inviting authors
to add more. The reviewer filed the verdict as a `COMMENT` review, supplied
the failing test, the fixing session became a co-author and said so, and a
*third* session merged. The boundary did what it is for.

**The convergence-point rule worked at the scale it was written for.** The
content PRs collided at the same five points — `contents.json`'s design
order, two constant tails, the search fixture, and the coverage test blocks
at the tail of `user-guide.spec.ts`. #497's and #500's merge commits each
record the reviewing session merging `main` *"at the five convergence points
both PRs named"*, and #501's did the same (its pre-squash merge `9515edf`,
and its first review). Each claim comment had named them in advance as
trivial; each resolution was mechanical under `review.md`'s carve-out; and
#501's records diffing the two merged coverage tests byte-for-byte against
their copies on `main` to prove nothing was lost. **Not one of the collisions
was a logic conflict**, and the two PRs that shared no convergence point —
#504 and #505 — merged into each other cleanly, which I checked directly by
merging post-#504 `main` into #505 before merging it.
`operating-model.md`'s "Textual conflict is not dependence" is doing exactly
the job #431 wrote it for.

**CI stayed green throughout.** The last **31 CI runs (421–451) all
succeeded on the first attempt**, with no retries, and the last **14 Pages
deployments (199–212) all succeeded** — including runs 449, 450 and 451, the
three merges from this session. No flake was filed and none was needed.

## Went poorly

**The README drifted, because a rule told sessions to feed it.** Until #486
the README carried ~500 lines of per-feature narrative, one paragraph per
feature with its issue numbers, and `development.md`'s Definition of Done
listed *"associated documentation (README, ADRs, user-facing docs)"* — so
the correct move on every feature PR was to add another paragraph to a
document nothing checked. The drift is not hypothetical: at the moment this
session picked #486 up, `README.md` on `main` said of the guide *"It ships
with Quick Start and Concepts; the feature pages follow (#479–#486)"* — six
guide PRs after those pages had started landing, with nineteen sections in
`contents.json` and the Feature Index among them. A document describing its
own replacement, five merges out of date, on `main`.

The hand-over also shows what the narrative had accumulated. Of the 102
issue numbers it cited, the mapping to guide pages covers 99; the three left
over are not features — #479 and #486 name the guide's own construction, and
#488 (*Copy chapter list on export*) is a forward reference to unbuilt work.
That last one is honest in itself (it names the issue), but it is the kind
of sentence that only makes sense to someone reading the backlog, and it
sat in the product's front-page description. Fixed structurally rather than
by resolve: the narrative is gone, the guide has a CI walk, and the
Definition of Done bullet now says which document holds what and why a
feature paragraph must not come back.

**A PR body's count did not match its own diff.** #505 said *"Twenty-one
links, no prose"*. Seventeen-plus-four *lines* was exactly right and I
verified it mechanically; the number of **links added was 29**, because the
sentence's own enumeration below it de-duplicates two links counted under
two headings and omits eight more that are in scope but unlisted. The work
was correct and the review merged it. It is recorded because it is the same
*shape* as #469 last period — a figure in a PR body that reads as a diff
statistic and is not one — and #471 already governs the case where the
figure answers an acceptance criterion, which this one does not. One
instance either side of that rule's boundary is not a pattern; it is written
down so a third is recognizable as one.

**A PR could not measure its own central claim, by construction.** #506's
entire content is the factual claim that GitHub refuses `REQUEST_CHANGES`
from the authoring account. Measuring it means submitting one — and the only
pull requests available to the authoring session were its own *open* ones,
where a stray changes-required verdict is exactly what the invariant exists
to prevent. That session declined, corroborated from #501's review record,
and said plainly in the PR body that it had not re-run it. That was the
right call and the honest one. The reviewing session could measure it
safely, and did: submitting `REQUEST_CHANGES` against the **already-merged**
#504 returned

```
Review Can not request changes on your own pull request
```

byte-for-byte the string the PR writes into the rules, and created nothing.
The gap is not that anyone behaved badly — it is that nothing told either
session where a refusal-shaped probe can be run for free. → proposed below.

## Changes proposed

- **Say where a refusal-shaped API behaviour can be verified: against a
  merged PR** — #508. One sentence in `review.md`, beside the paragraph that
  already records both refusals. A session that needs to *check* what the
  API does, rather than take the rules' word for it, has a free place to do
  it: a merged PR accepts the probe if the API would accept it at all, and a
  refusal creates nothing. Without that sentence the only options a session
  sees are its own open PRs — where being wrong is costly — or not checking.
  Evidence: #502 measured it accidentally while reviewing #501; #506 could
  not re-measure it and said so; #504, already merged, cost nothing.

Nothing else. The convergence points, the authorship handling and the
green CI are recorded as the rules working; the #505 count is one instance
on the far side of #471's boundary and is recorded, not legislated.

A separate piece of ordinary engineering work came out of reviewing #504
and is filed as #507 rather than proposed here: the Feature Index walk does
not open the visual editors, the recording dialog, Open project or Save
mode, and five controls behind those doors — *Stop recording*, *Choose
media files…*, *Embed media in the project file*, *Store references only*,
*Show result* — are explained in the guide's prose but missing from the
index, with CI green. Engineering work, not process: the rule is right and
the check is real; it is the coverage that is narrower than it reads.
