## Went poorly

**A behaviour change corrected three guide passages and shipped a fourth
that contradicted them.** #561 made the undo chords wait behind a modal
dialog, and its author found the three pages that said the chords pause
*only* inside text fields and corrected all three. `docs/guide/timeline.md`
line 30 said the same thing in different words and was not found. The
reviewing session ran one grep for the old wording, got four hits, saw the
PR had changed three, and pushed the fourth as a one-line alignment
(`8774be0`) under `review.md`'s trivial-fix carve-out. The author did the
hard part — knowing the behaviour was described in several places — and
missed the mechanical part, because nothing asked for the mechanical part.
The guide describes one behaviour from several pages by design, so a
behaviour change always has more than one passage to find, and reading is
how one gets missed. → proposed below.

**An issue's claim about repository state was written from memory and was
wrong.** #536 stated, in bold, that *nothing is missing from the guide —
every control below has an index entry*. Three of the four were not
indexed; `grep -nE '^- \*\*(Chapter marker|Move to playhead|Name of
chapter marker)\*\*' docs/guide/feature-index.md` returns nothing (exit
1) on the `main` the issue was written against, `45f9615`, and returns
all three on `main` today. The anchor matters: the same terms grepped
unanchored match twice at `45f9615`, on lines 38 and 154, but both hits
are the `› Chapter markers` link text inside *other* entries — which is
the distinction the issue's claim turned on. The implementing session
found it because the walk reported it, recorded the correction on the
issue at claim time, and added the entries — so the outcome was right,
and the walk did its job.
But `process-improvement.md` already says a citation a later session will
rely on gets looked up, not recalled, and this is that rule applied to a
claim rather than a citation. Recorded, not legislated: the rule exists;
one instance is a reminder to read it as covering claims.

**The reviewer's own near miss: an executable claim written before the
command was run.** This session's reviews of #562 and #563 stated
"`git merge-tree` against the other two: clean" — a true statement, but
one the session had *inferred* from the disjoint file lists and wrote into
both reviews before running the command. The command, run next with three
arguments instead of two, failed on every pair, and for a moment the
session had two posted reviews saying "clean" and a terminal saying
`CONFLICT`. Re-run correctly (two branches, `--write-tree`), all three
pairs merged clean, so nothing false shipped and nothing was merged on a
wrong claim. `process-improvement.md` says a retrospective or issue
proposing a command must have run it; a *review* stating a command's
result is the same obligation, and the fix is the habit the rule already
names — run it, then write what it returned — not a new sentence.
