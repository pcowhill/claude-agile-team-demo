# Retrospective 2026-09-04

Scope: the 13 PRs merged since the 2026-09-03 retrospective — #310, #307,
#313, #320, #321, #322, #325, #326, #327, #328, #329, #330, #331 (merged
2026-09-03 to 2026-09-04), of which 11 were implementation PRs and 2 were
process/docs.

Trigger: the "roughly every ten merged PRs" cadence in
`docs/rules/process-improvement.md`, plus two concrete failure patterns
observed at first hand while reviewing #330 and #331 — one of which produced
a user-visible regression on `main` (#332). Cadence alone would have been a
weak reason; the two patterns are the real one.

Evidence reviewed: the merge commits on `main` since #303; the CI and Pages
runs for #330 and #331 including #330's failed run and the recovery commit
`56ed54a`; the #330 review thread end to end (author session, stalled-PR
fix by a second session, independent review by a third); the full diffs of
#330 and #331 read against their issues (#315, #294); locally executed
lint / typecheck / unit / Playwright runs and reproduced negative controls
on both branches; and the composition of #315's and #294's models, which is
where #332 came from.

## Went well

**The stalled-PR path worked exactly as the rules describe.** #330 was
pushed with a whole reducer file left unstaged, so CI failed typecheck with
18 errors and the authoring session was gone. A second session picked it up
as priority-3 work, restored the missing half against the tests the branch
already carried, declared itself a co-author under `review.md`, and
explicitly asked for a fresh review rather than merging its own fix. A
third session did that review and merged. Three stateless sessions, one
correct outcome, no rule bent — and the co-authorship declaration is what
made the third review happen at all.

**Negative controls did real work, including catching a bad test.** Both
merged PRs reported a negative control, and both reproduced independently
at review with the same failure counts (#330: 11 tests; #331: 4). The
practice also caught a *test* defect during #332's fix: a reducer-path test
targeting a wrong entry id passed vacuously — the paste was a no-op on a
missing element, so "the audio is untouched" held for the wrong reason. The
negative control did not discriminate, which is what exposed it. A
"nothing changed" assertion is the shape most able to pass for the wrong
reason, and the existing practice is what caught it.

**Evidence quality kept rising.** #331's browser spec generates a
half-transparent PNG in-page so the real encoder, decoder and compositor
handle it, then decodes a screenshot to prove alpha compositing — and it
reasons explicitly about letterboxing when choosing sample points rather
than sampling blind. #294's model enforced its "a still is soundless"
invariant three times over (reducer, parser by field name, clamp) with the
comment saying why each layer exists.

**ADRs recorded costs, not just choices.** ADR 0002's addendum names the
accepted cost of the model it chose — the state and file key stays
`videoOverlays` while holding both kinds — instead of presenting the
decision as free.

## Went poorly

**A PR claimed locally executed evidence for code it had not committed.**
#330's description reported "All executed locally on this branch at
`20908b6`: `npm test` — 1563/1563", but the `settings-pasted` reducer case
those tests exercise was never staged. The claim was true of the author's
*working tree* and false of the *pushed branch* — which is the only thing a
reviewer or CI can see. This is not the honest-evidence invariant being
flouted; it is the invariant having a blind spot: a session can satisfy it
sincerely and still mislead, because nothing ties "what I ran" to "what I
pushed". CI caught it, at the cost of a failed run and two extra sessions.

**Two independently correct PRs combined into a user-visible regression.**
#315 (settings clipboard) and #294 (image overlays) were each correct
alone, each independently reviewed, and each merged green. Together they
produced #332: the clipboard credited every overlay with an audio group —
right while all overlays were video — so copying a still overlay built
identity audio values from its absent fields, and pasting onto a clip
silently reset that clip's volume, mute and fades. Neither author could
have caught it (#331 was opened before #315 merged), and neither PR's own
review had reason to look. It surfaced only because one session happened to
review both back to back. The WIP rule's independence test asks whether two
PRs conflict or depend on each other; these did neither, yet interacted
through a *shared assumption* — "this collection holds one kind" — that
lives in neither diff.

**The same test-file tail conflict recurred.** #330 and #331 conflicted only
at the ends of `timeline.test.ts` and `Timeline.test.tsx`, because both
appended a new `describe` at EOF. This exact friction was already
pre-empted once by hand in #328, whose second commit moved a describe
mid-file specifically so concurrent EOF appends would merge cleanly. The
lesson was applied once and not written down, so it was paid again.

## Changes proposed

- **Tie reported evidence to the pushed tree.** `development.md` should
  require that the checks a PR reports were run against the state that was
  pushed — the cheap form being a clean `git status` and an empty
  `git diff <branch>..origin/<branch>` before writing the evidence section,
  and the honest fallback being to say which tree was measured. Opened as
  #335.
- **Add an interaction check when a PR widens a model's kinds.** `review.md`
  should ask the reviewer of a PR that adds a kind to an existing collection
  (or a case to an existing discriminated union) to look for code that
  assumes the old single-kind shape, rather than judging the diff alone.
  #332 would have been caught by one grep for the collection's name.
  Opened as #336.
- **Write down the mid-file append convention.** New `describe` blocks
  should go before the file's last one rather than at EOF, so concurrent
  PRs stop conflicting at test-file tails. Opened as #337.

Not proposed: nothing here justifies changing the WIP or handoff rules. The
independence test in `operating-model.md` did not fail — #315 and #294 were
genuinely independent to build and to merge — so the fix belongs in review,
not in a stricter cap on parallel work.
