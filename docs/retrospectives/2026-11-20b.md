## Went poorly

**A flake watch closed by count after its cause had been measured, and
recurred within the hour.** #788 watched `record-webcam.spec.ts:33`.
- By 15:51 its thread said a fix would *"pay for itself sooner than the
  watch would"*.
- At 16:15 it turned `main` red (44771561941).
- At 17:29 #789's dispatched measurement explained it: the recorder starts
  about 0.4 s behind the readout, so a take stopped at `0:01` can list as
  `0:00`. The comment named the fix, *"record until the readout shows
  0:02"*.
- At 19:15 it closed at five clean runs, as `quality-and-ci.md` says.
- At 19:59 it recurred: #810's first run went red on all three Firefox
  attempts (44807191510). At 20:05 it came back again, flaky in Chromium on
  `main` (44808139430).
- #812 and #813 then shipped the fix named at 17:29.

Every session followed the rule. The rule's only exit for a watch is the
count, and it was written for "a failure seen once that will not fail
again on demand". By 17:29 #788 was neither. Proposed: #817.

**#814's broader question, whether the recording specs should share one
rule for take length, gets no proposal.** #814 listed four timing failures
in recording specs. Read closely, they are not one mechanism:
- #788 / #812: a fixed recorder start latency, now fixed in the spec
  (#813).
- #806: a 0.6 s floor missed only under local 3-worker oversubscription,
  never in CI. It closed by count today, with no cause measured. That fits
  #817's wording, since it is still a flake nobody has explained.
- #801: Firefox losing part of a paused take's audio, which is a file
  defect, not a timing margin.
- #783: the screen recording dialog.

A shared "take length" helper would have fixed only the first, which is
already fixed. If #806 recurs in CI, its issue already says to look at the
take length the spec records, and #373's media-span probe in
`record-screen.spec.ts` is the model.
