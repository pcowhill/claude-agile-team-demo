# Retrospective 2026-08-27

Scope: the fourteen implementation PRs merged since the fourth retrospective
(#125): #130, #131, #132, #147, #148, #149, #150, #152, #155, #156, #157,
#158, #159, #160.

Trigger: fourteen implementation PRs merged since the last retrospective —
nearly triple the "roughly every five" cadence in
`docs/rules/process-improvement.md`. No recurring failure pattern forced an
earlier one; the backlog simply moved faster than the retro cadence.

Evidence reviewed: the merge commits on `main` since `79f00a9` (#125); all 30
main-branch workflow runs in the period (CI runs 111–136 and Pages deploys
53–68, each checked for its conclusion); the review records on #159 and #160;
and the #133/#134 feedback triage chain (#137–#146) as filed and cross-linked.

## Went well

**Main was green the entire period.** All 30 main-branch runs concluded
`success` — zero broken-main incidents across fourteen merges, and every
deploy launched only after its commit's CI succeeded (the #106 gate keeps
holding). The suite stood at 767 unit tests and 70 Playwright tests, all
passing, at period end.

**Customer feedback decomposed into serialized chains that sessions actually
respected.** #133/#134 (layered clips, text on video) became #137–#146 with
explicit "serialized, do not start while X is unmerged" dependency notes.
Every chain landed in order — media/model first, UI + preview next, export
last — and each PR stayed independently reviewable at a few hundred lines
instead of one multi-thousand-line feature drop.

**Preview/export parity is now a working discipline, not a hope.** Text
overlays (#158/#159) and video overlays (#160/#161-in-flight) both shipped as
shared pure helpers consumed by both renderers (font/line math, window
selection, placement rectangles), with the parity criterion the session
cannot assert named **customer-verifiable** in the PR per
`product-management.md` — honest evidence instead of overclaiming, twice in a
row.

**Parallel work predicted its own conflict and stayed cheap.** The session
that opened #159 and #160 in parallel disclosed in the PR body exactly where
they would collide (one README sentence, one CSS block). The conflict
materialized when #159 merged first; the reviewing session resolved it as one
trivial merge commit, validated the combined tree locally, and merged #160
the same day. Disclosure turned a surprise into a checklist item.

## Went poorly

**#149 was merged with a merge commit instead of the preferred squash**
(`review.md`), the only non-squash merge in the period. Consequence is
cosmetic but real: the branch commit (`a1a9f12`) and the merge commit
(`e2598f7`) both sit in `main`'s history carrying the same change and nearly
the same message, so history greps see #143's slates land twice — this retro
initially misread it as a direct-to-main push.

**"Genuinely independent" was stretched by #159/#160.** Both rewrote the same
README feature-summary sentence and touched the same CSS file — textually
entangled even though the features were. The cost was minutes because the
author disclosed it, but the lesson generalizes: two feature PRs that each
update the one README summary paragraph are never conflict-free, whatever the
code says. Sessions weighing the `operating-model.md` independence test
should count shared prose (README, doc summaries) as shared code.

## Changes proposed

None rising to a `process` issue. Both misses are adherence/awareness notes
already covered by existing rules — `review.md` states the squash preference,
and `operating-model.md`'s independence test already asks whether merging one
PR conflicts with the other. Recording them here, where orienting sessions
will find them, is the proportionate fix.
