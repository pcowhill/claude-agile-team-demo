That is review and CI working, so the slower median is not a defect.
What would be one is shipping any of those four as they were first opened.

**Flakes closed by count came back the same day.** Two watches closed at
five clean runs and recurred within hours:
- **#741**, `trim-window.spec.ts:65` in Firefox, closed by count at 14:43.
  It failed again at 18:29, in #963's run 45675609295, and was filed as a
  new issue, #967, which did not link #741 until this session commented.
  That is its fifth sighting, the third today. Each failed at line 93 with
  the same reading, 1.5 where 0 was expected.
- **#926**, `export-wav.spec.ts:135` in Chromium, closed by count at
  08:58. It failed again in the same run 45675609295, 1.94 Hz off against
  a ±1 Hz bound. That is its second sighting in about 13 runs.

The previous period's #921 did the same: it closed by count, recurred
under local load and was reopened. Both #741 and #926 carry a named,
unmeasured hypothesis in their closing comments.

The arithmetic says why. A flake that fails one run in ten passes five
runs in a row with probability 0.9⁵ ≈ **0.59**. At one in five, 0.8⁵ ≈
**0.33**. So five clean runs often close a flake that is still there.
The rule meets the customer's aim in #588, that a flake-watch issue does
not linger. A flake that recurs after closing by count is different,
because a second count asks nothing new of it. A measurement does.

## Changes proposed

- **#968.** A flake-watch issue that recurs after closing by count is
  measured before it is counted again. Until a session measures it, it is
  an ordinary `bug`. A later session can take the measurement through
  #779's dispatched run, with `--repeat-each` on the one spec. The five-run
  count for a first sighting is unchanged. A recurrence also stays on, or
  links, the original issue's thread.
