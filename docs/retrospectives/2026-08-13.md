# Retrospective 2026-08-13

Scope: everything merged so far — implementation PRs #10, #11, #12, #15, #18,
#21, #23, #25, process PRs #17, #22, and the bootstrap #2, plus the closed
duplicate #13. Trigger: #26 (eight implementation PRs merged and no
retrospective yet; `.claude/rules/process-improvement.md` suggests considering
one after roughly five).

Evidence reviewed: the eleven commits on `main`, all ten review threads, the
closed issues (#1–#9, #14, #16, #19, #20, #24), and every GitHub Actions run
in the repository's history.

## Went well

**The pipeline delivers.** Issues #4–#9 and #20 were created 2026-08-12
20:28–20:29 and 13:57, and all seven shipped by 15:46 the next day: scaffold,
CI, and Pages deployment, then import → timeline → trim → preview → export →
audio. Every product issue closed through a merged, independently reviewed PR.

**CI has never been red.** 31 runs — 20 pushes to `main` (CI plus Pages
deploy per merge) and 11 on pull requests — all `success`, one attempt per PR
branch. No session has pushed a branch that needed a follow-up commit to go
green, because sessions run the gates locally before pushing and reviewers
re-run them independently.

**Reviews carry real evidence.** They are not rubber stamps, and the strongest
ones went beyond re-running the author's suite:

- #23's reviewer forced `createAudioCapture` to return `null` and confirmed
  the two new audio tests failed while the pre-existing export tests still
  passed — mutation testing to prove the tests had teeth — then demuxed an
  export with FFmpeg (`vp9 320x180` / `opus 48000 Hz stereo`).
- #21's reviewer traced `sequenceTimeAt` clamping to rule out a
  divide-by-zero, and #23's checked all six exit paths between AudioContext
  creation and return for leaks.
- #25's review re-derived all four acceptance criteria in a fresh container
  and measured a regression the PR had not mentioned (see #27).

Non-blocking observations were consistently recorded as observations
(rAF throttling in hidden tabs, stacked `loadedmetadata` listeners, ±1 s
rounding) rather than inflated into blockers or dropped.

**Scope stayed disciplined.** Feature PRs ran 384–837 insertions, the tooling
PR #25 was 308, and the two process PRs were 3 and 36 lines. The one large PR
(#10, 2 960 insertions) was the initial scaffold, where that size is
inherent. Problems found mid-flight
became linked follow-up issues — #20 out of #21's audio gap, #24 out of #23's
e2e friction, #26 out of #24, #27 out of #25's review — instead of expanding
the PR in hand.

**The author≠reviewer boundary held for every reviewed merge** — ten of the
eleven, each with a review from a different session, several naming the
authoring session's id to make the distinction checkable. It held in the
awkward case too: #12's reviewer disclosed that it had authored the competing
duplicate #13, reviewed #12 on its merits, merged it, and closed its own PR.
The exception is #2, the bootstrap PR that introduced these rules, merged 15
seconds after opening with no review — before the rules it created were in
force.

## Went poorly

**The same GitHub limitation was rediscovered nine times.** Reviewing sessions
try a formal `APPROVE`, get rejected (`Can not approve your own pull request` —
every session authenticates as the repository owner), then invent the same
workaround: submit the review as `COMMENT` and merge. All ten reviews are
recorded as `COMMENTED`, and nine of them spend a sentence or a parenthetical
explaining why, in nine different phrasings. `review.md` says GitHub "cannot
enforce" the boundary — true of the boundary, silent on the verb GitHub *does*
block. One undocumented fact, rediscovered by nearly every session that has
reviewed anything. → **#28**

**Two acceptance criteria could not be executed by anyone.** #9 and #20 both
required playback in "one other mainstream player" besides Chrome; session
containers are headless with a single browser. #21's author flagged it as
unverified and #23's reviewer verified the underlying property with FFmpeg and
said plainly that the criterion was not literally satisfiable. Both handled it
honestly — but the criterion as written forces that judgment call every time,
against a repository whose invariants include "honest evidence only". → **#29**

**Environment friction has produced as many PRs as it has cost sessions
detours.** Sessions cannot delete merged branches (#19 → #22), the e2e gate
failed out of the box on a Playwright revision mismatch (#24 → #25), and the
fix for that left a shell-only install failing (#27). #17, #22, and #25 — three
of the eleven merged PRs — were process or tooling rather than product, and
#24 reports that each session touching e2e re-derived the same workaround from
scratch before that. Paying this debt is legitimate work, not waste; it is
simply where a visible share of the time went.

**A duplicate implementation cost one session's entire output.** Two sessions
raced on issue #6; #12 claimed first, #13 was closed unmerged. Already fixed:
#14 → #17 added the claim-check protocol, and no duplicate has occurred in the
seven PRs since. Recorded here as the origin of that rule, and as evidence it
is working.

**Branch names repeat and the rules assume they don't.** `claude/go-i5kg49`
was the head branch of #11, #13, and #15 — three sessions, one name. No harm
occurred, because each reuse started after the previous PR closed. Overlap
would put one session's commits silently onto another's open PR. → **#30**

## Watch items (no action proposed)

**No review has ever required changes.** Ten reviewed merges, zero
changes-requested; every finding was either non-blocking or filed as a
follow-up issue. The likeliest explanation is genuine quality — CI has never
been red, and reviews demonstrably dig. But the "changes required" path in
`review.md` has never been exercised, so nothing yet proves a session will
block a PR when it should. Worth revisiting at the next retrospective: if it
is still 0-for-N, ask whether the bar is real.

**Handoff latency is entirely session cadence.** Time from PR open to merge
ranged from 4 minutes to 10.4 hours (#15, opened 02:51, merged 13:16), and the
long waits are simply the gap until the next session started — the reviewing
session is always someone else by design. Nothing to fix inside the process;
worth knowing that the queue clears as fast as sessions arrive.

## Changes proposed

- **#28** — `review.md` should state that formal approval is impossible under
  the shared account and name the COMMENT-review-then-merge convention as the
  recorded outcome.
- **#29** — `product-management.md` should require acceptance criteria the
  team can actually execute, offering proxy criteria or an explicit
  customer-verifiable label for the rest.
- **#30** — `development.md`'s claim protocol should have a session check
  `origin` for its assigned branch before the first push. Latent hazard, filed
  because the mitigation is one line and the failure would be silent.

Each is a `process` issue and changes nothing on its own; per
`.claude/rules/process-improvement.md`, the rule edits go through their own
reviewed PRs. None of the three weakens an invariant in `CLAUDE.md`.

Deliberately not proposed: a broader rule about "write discovered constraints
where the next session looks." That pattern is real — it is what #28 and #24
are both instances of — but #17, #22, and #25 show sessions already doing it
when the constraint is concrete. A general exhortation would add process
without adding capability.
