## Went poorly

**A test flake reached `main`, and it is a class rather than an instance.**
#444's `e2e/overlay-editor.spec.ts` asserts a keyboard nudge and its undo
by reading the field once, immediately after `page.keyboard.press`. That
call resolves when the event is *dispatched*, not when React has committed
the render it causes, so the read can catch the pre-undo DOM. It passed
alone, passed in three full-suite runs, and then failed the first
full-suite run that carried a 220th test — this session's crop spec, which
had copied the same shape and failed beside it. Measured in the new spec:
**2 failures in 5 repeats** at `--workers=2`, **0 in 20** once the reads
became polled assertions.

Both are fixed (#446 carries the one-line fix to #444's spec), but the
shape survives: `grep -n 'inputValue()' e2e/overlay-editor.spec.ts` on
`main` returns nine reads, two of them the pair just fixed, leaving seven
across five more assertions of the same kind. Two sessions have now written
it independently, neither with a reason to know that a bare read after a
synthetic input is a race, and #424's acceptance criteria ask for exactly
that measurement next ("a drag by a known offset commits `x`/`y` within
0.005"). Nothing in the repository says so. `e2e/zoom-editor.spec.ts` is
clear — it reads no input values at all — so this is two instances, not a
pattern across all three editors.

This is the second flake finding in two periods: #442 recorded a unit test
that failed once under load and would not reproduce, and its own advice was
to capture more next time rather than chase it. That one is still one
sighting. This one is diagnosed, reproduced on demand, and fixable by
convention.

**Two comments shipped describing code that had stopped being true.** This
session pushed two comment-only fixes while reviewing: `#445` left
`e2e/timeline-sliders.spec.ts` explaining a measurement by
`.audio-track-gain input`, a selector that PR removes; `#444`'s new tests
said rounding was "to a thousandth" where `RECT_DECIMALS` is 2, and called
a 0.35 × 0.2 box "2:1". Each is trivial and each passed both authoring and
review. Worth recording as an observation, not a proposal: the first is the
kind of thing `review.md`'s widened-kinds grep would catch if it extended
to comments, the other two are arithmetic slips no rule prevents, and one
day's worth of two different causes is not evidence for a rule.

**CI's browser job broke for the whole repository, and the guard that
exists for apt trouble could not help.** From about 17:45 UTC today every
Playwright check fails 25 seconds in: `install-deps` runs `apt-get update`,
and `dl.google.com` is serving a `Packages.gz` whose SHA256 does not match
its own `InRelease`. The workflow already carries two retry steps for apt
(#85, #89) — kill the leader, repair `dpkg`, fetch again — and they ran and
failed, because re-fetching is exactly what a corrupt index defeats. Filed
as #447 with a fix in #448.

The finding is not that the mirror broke; that is nobody's doing. It is
that the job consults a third-party index it has no use for at all —
Chromium's system libraries come from Ubuntu's archives, and the Google
Chrome list is in the runner image for a browser these tests never launch.
A dependency nothing needed took every required check down at once.

## Changes proposed

- **Say that a test must not read a value straight after a synthetic input**
  — #449. `quality-and-ci.md`'s flaky-tests paragraph should name the
  mechanism, because it is not guessable from the outside and three
  sessions have now written the same racing shape: a driver's
  `keyboard.press` / `mouse.up` resolves on dispatch, not on the framework's
  commit, so an immediate one-shot read can see the previous render.
  Auto-retrying assertions (`toHaveValue`, `expect.poll`) are the fix, and
  reading two values that must agree needs them inside one poll. With the
  measurement that makes it concrete — 2-in-5 under `--workers=2` versus
  0-in-20 — and a note that the failure hides until suite load grows, which
  is why it survived three green full-suite runs and #442's sibling is
  still unreproduced.

Nothing else. The stale-comment observation above is deliberately not a
proposal, for the reason given there. #447/#448 is an incident with a fix
already open and needs no rule. And the closed watch item is closed rather
than replaced: this period's evidence argues against a cap below the WIP
limit, not for one.
