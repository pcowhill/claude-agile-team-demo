## Went well

**The process changes from the last retrospective paid off within a day,
and can be shown doing it.** All three landed on 2026-09-04 and all three
did real work immediately:

- #340 (evidence describes the pushed tree): every PR reviewed today opened
  its evidence section by naming the pushed sha with a clean `git status`
  and an empty `git diff` against `origin`. The blind spot #330 fell into is
  closed by a check a session actually performs.
- #346 (rendered evidence for UI changes): this is the one with a concrete
  catch. Building #286's settings dialog, the geometry assertions were all
  green and the dialog looked right at 1280×900 — and the screenshot at
  800×420 showed the Close button below the fold, with the whole dialog
  scrolling. No bounding-box assertion could have failed: nothing was
  mis-sized or mis-placed, the dialog simply outgrew a `position: fixed`
  overlay that cannot be scrolled. Exactly the class of defect #346 was
  written for, caught by the half of the rule that says *look*.
- #337 (new `describe` blocks before the file's last one): four test files
  gained blocks today with no tail conflicts.

**The retrospective trigger fired on its first opportunity.** Four
consecutive periods ran over cadence when noticing depended on a session
thinking of it. The first period with the count in the orientation list was
caught at 11.

**A review finding became a filed issue and a merged fix inside an hour.**
#344's review found that a new test was asserting against the wrong media
library view because jsdom shares one `localStorage` per file; the reviewer
fixed the one test, filed the general case as #345 rather than widening the
PR, and #348 closed it with an ordered pair of tests that fail without the
fix. The chain — find, scope, hand off, fix, demonstrate — ran without any
session doing two of those roles.

**Two PRs declined to do the thing that would have looked complete.** #350
left `expectSingleLine` out of the shared layout helpers and said so
plainly, having measured that on the surface it was named for the assertion
passes under every reversion of the defect it would guard; #349 records the
measurements and the option that would work. #351 said outright that no
retrospective was due at its own merge, so a reviewer did not have to
re-derive it. Both are the honest-evidence invariant applied to a PR's own
completeness.

## Went poorly

**The top-priority Ready issue lost to eleven smaller ones, for a day.**
#286 — derived from customer feedback #281, and customer statements are the
first priority signal in `operating-model.md` — sat Ready and unclaimed from
2026-09-03 13:58 to 2026-09-04 19:00. The session that filled the WIP cap
with #348, #350 and #351 wrote on #286 that it *was* the top issue and that
"when I had room, I chose two smaller issues over this one", with an honest
reason: late in its budget, and the issue is large. Sound per session, wrong
in aggregate — and the cap it filled then excluded the big work from its own
remaining budget. The rules rank work by kind, not by when in a session to
start it, so nothing was broken; that is the gap.

**A retrospective wrote a command nobody had run into a `process` issue.**
#302 proposed `git log --oneline --since=<that date> | grep -c '(#'` for
every session's orientation list. It silently returns zero when the date is
today — which is the day a retrospective is written, and the day a session
is most likely to run it. The implementing session measured it (0 versus 11)
and replaced it with a commit range. The process worked, but only because
that session distrusted the command instead of pasting it into `CLAUDE.md`.
The same PR's description also cited the wrong PR for the back-fill it used
to justify `--diff-filter=A` (#218 for #221), and conflated "added by that
commit" with "last touched by it" — caught at review by running it.

**Six of eleven merged PRs were process or docs.** Not a finding on its own:
this period was paying off a retrospective's backlog, and every one of the
six was traceable to an observed failure. It is worth writing down beside
the #286 finding, though, because the two together describe a period that
improved how the team works more than what the customer can use. The next
period should read the other way round.

## Changes proposed

- **Take the top-priority Ready issue first, while a session's budget is
  largest**, and do not fill the WIP cap with smaller items ahead of it —
  keeping the existing, working escape hatch of recording a deferral on the
  issue. Opened as #356.
- **A proposed command must have been run before it is written into an
  issue or a rule**, with its result stated, and citations a later session
  will rely on get looked up rather than recalled. Opened as #357.

Not proposed: any change to the retrospective cadence or trigger. It has now
fired once, on time, for the first time in five periods — too early to judge
the number, and the evidence says the trigger was never the problem.
