## Went well

**The period was pure product delivery, and most of it came from the
customer's own words.** Thirteen implementation PRs and no process PRs at
all, against 10/2 last period and 5/6 the one before. Six
`customer-feedback` issues arrived in a single burst on 2026-09-05 (#380,
#394, #395, #396, #397, #398) and every one was triaged, decomposed, and
either shipped or scoped into Ready work inside the period. Four AI
suggestions were approved by the customer and captured the same way (#316 →
#379 → #383, #381 → #385 → #387, #386 → #388 → #390, #389 → #391 → #393),
each on an explicit go-ahead comment — "Yes, I like this. Implement it." on
#389 is typical — never on ambiguous enthusiasm. The customer asked for
proactive suggestions in #166/#173; this is the first period where that
pipeline carried roughly a third of what shipped.

**The two hardest pieces of feedback became design questions instead of
guesses.** #395 ("So Many Buttons") and #396 ("Add More Graphic Tools")
were open-ended UX directions — exactly the shape that tempts a team to
invent scope. Product management turned each into a `customer-question`
carrying a concrete design, its tradeoffs and a recommendation (#401,
#402). The customer approved both *with one modification each* — put Split
inside the preview's Frame menu; add a Settings switch to disable the
visual editors, because of the render cost — and both modifications are
visible in the shipped code: `AppSettings.visualEditors` exists in #428
because #402's answer asked for it. Each approval was then decomposed into
phased issues with the approving comment linked. This is the
customer-question mechanism doing exactly what it is for, on the two items
where guessing would have been most expensive.

**The "Retrospective due" route worked on its first use.** #302's finding
was that the trigger was stated but nothing made a session *notice* it —
four consecutive periods ran over cadence, one by 31 PRs. This period a
session ran the count, found exactly 10, had higher-priority work (two
answered customer questions to translate, Ready work to implement), and
filed #414 with the command and its output, rather than either holding the
retrospective out of turn or letting the finding evaporate. The next
session with a clear board inherited it from the backlog. First exercise of
that path; it cost the filing session a few minutes and saved the finding.

**Rendered-evidence discipline caught a layout defect before the customer
did.** The rule in `development.md` exists because two layout defects
reached the customer under green CI — the export modal's overflowing format
note (#268) and the cheat sheet's mid-combo wrap (#287), both reported by
the customer with screenshots. This period #408's author, inspecting the
export modal's screenshot as the rule requires, found the *pre-existing*
Frame rate field rendering past the dialog's right edge: the same shape of
defect, on the one fieldset the layout spec had never measured. It was
filed as #407 rather than folded into #408 — scope discipline — and #409
fixed it with a test that fails without the CSS change at the exact numbers
#407 reported (right edge 910 vs 833). Third instance of the class, and the
first the team found itself.

**Evidence honesty held on the details nobody would have checked.** Both
#428 and #429 disclosed that their full suites had run on a tree differing
from the pushed one — by one JSX block's indentation, and by a re-wrapped
doc-comment line — and named exactly what was re-run afterwards on the
pushed commit, with `git status` clean and `git diff` against the remote
confirmed empty. Neither difference could have changed a result, which is
precisely the case where saying nothing is tempting and #335's lesson would
quietly erode. It did not.

## Went poorly

**The independence check passed two PRs that then conflicted.** One session
again filled all three WIP slots (#427, #428, #429). The last retrospective
recorded that concentration as a watch item and said the case for a rule
"should wait for an instance where it actually hurt". This period supplies
a small one.

#428 and #429 both modify `Timeline.tsx`. Both claim comments reasoned
about *hunks* and concluded any merge order was fine — #413's said it
"touches the zoom block of `Timeline.tsx`"; #404's said it "moves the
inline `NameField` out of `Timeline.tsx` (its own block near the top of the
file, far from #428's zoom hunk)". Both were right about the hunks. Both
missed that each also adds one line to the same import list, immediately
after `import { ConfirmDialog } from './ConfirmDialog'`. Merging #428 left
#429 un-mergeable, and the reviewing session had to resolve the conflict
before it could merge.

The cost was one trivial resolution — two adjacent imports, both kept — so
this is a small finding, not a wound. It is worth recording because it is
the same *shape* as a lesson `development.md` already carries about test
files: "the end of the file is the one line they all reach for", so
concurrent PRs turn a clean merge into a tail conflict. An import list is
that line for a component file, and every PR that adds a component to
`Timeline.tsx` reaches for it. The current wording invites the wrong
answer: `operating-model.md`'s independence test asks whether "merging one
does not conflict with the other", and two sessions reading it honestly
both answered no — because they were reasoning about behaviour and hunks,
not about the few lines every such change converges on. Proposed as #431.

**Three PRs, ~3,360 added lines across 42 files, one reviewer, no second
perspective.** The
same concentration as last period, larger. All three were sound and merged
in one pass, and the reviewing session did find a real defect — #427's
submenu flip measures the room available against the wrong anchor edge,
filed as #430 and linked onto #415, the phase that will first ship a
submenu. But the arithmetic is worth stating plainly: a single authoring
session produced every open PR in the repository, so nothing reached `main`
that more than one other session had seen, and there was no independent
check on the reviewer either.

Recorded as an observation again rather than a proposal, with one
refinement over last period's version: the cost is not review *quality* —
it held, twice now — but the absence of any second angle on a set whose
three PRs share one author's assumptions. A rule capping a session below
the WIP limit would cut throughput hard for a benefit nobody has yet
measured. The tripwire to watch is a defect reaching `main` that a second
author would plausibly have caught; #430 was caught, so this is not it.

## Changes proposed

- **Name the lines every concurrent PR converges on, in the independence
  test** — #431. `operating-model.md` should distinguish a conflict in the
  *logic* either PR changes (not independent; serialize) from a textual
  conflict confined to a file's *convergence points* — an import list, an
  export barrel, a registry every new kind extends, the tail of a test file
  — which is expected, cheap, and not a dependency; and should say that a
  claim comment names such a conflict instead of promising order
  independence, with the merging session resolving it under the mechanical-
  fix carve-out `review.md` already has.

Nothing else. The two mechanisms exercised for the first time this period —
#414's retrospective-due route, and rendered evidence catching a defect
before the customer — need no change, and the review-concentration item
above is deliberately a watch item with its tripwire stated. Opening a
`process` issue for it today would be the artificial activity
`operating-model.md` forbids.
