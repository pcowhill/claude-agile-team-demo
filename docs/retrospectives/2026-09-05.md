## Went well

**The balance flipped back to product, as the last retrospective asked.**
The 2026-09-04b period was six process PRs against five implementation ones
and said "the next period should read the other way round". It did: ten of
twelve were implementation or test work, and four delivered directly
customer-visible value — clip thumbnails captured at card size (#361, from
the customer's own diagnosis in #353), MP3 export (#363, from customer
feedback #264), a folded section's Expand all actually unfolding it (#364,
customer report #354), and the shaped-wipes transition pack on a new
registry extension point (#372, plugin roadmap #199/#183). The two process
PRs were not new ceremony; they paid the previous retrospective's two
proposals, both merged within a day of being proposed.

**The flake work ran as a pipeline across stateless sessions, exactly the
way this repository is supposed to work.** The #365 audit isolated defect
classes; each class became an issue carrying the recorded failure text, the
reproduction command (`--workers=8` oversubscription on a 4-core
container), the worked precedent to apply (#276's presented-frame decode,
#362's load-cannot-fake anchoring, #371's read+fill-in-one-retry), and — on
#370 — a deferral note in the exact #356 form naming what the implementing
session inherits. Five PRs (#367, #371, #375, #376, #377) then fixed the
classes serially, each by applying a pattern an earlier, unrelated session
had established; #376 is literally titled "adopt the suite's solved race
patterns". No session re-derived a diagnosis another had already recorded.

**Evidence discipline held under its hardest test yet: reporting stress
runs that were red for someone else's reasons.** #376's evidence names six
full-suite stress runs of which three were 166/167 — and states that every
failure was #370's class, on a branch that deliberately did not carry
#370's fix. #377 reports 165–166/167 the same way, and additionally records
two one-off failures it could **not** capture (later runs overwrote
`test-results/`), naming the specs and what a future session should do if
either recurs. The alternative — quietly rerunning until green, or bundling
the other branch's fix to make one's own runs pretty — did not happen
anywhere in the period.

**The #356 rule was exercised the day it merged.** #370's filer, having
authored two open PRs already, recorded a deferral note on the issue with
its reasons and what the next session inherits — the exact mechanism #368
codified — and the next session picked the issue up from that note alone.

## Went poorly

**Half the period's implementation capacity went to hardening tests against
a load level CI never runs.** Six of the ten implementation PRs (#366,
#367, #371, #375, #376, #377) were test-only, and five of those six chase
failures that reproduce only under `--workers=8` oversubscription — P3 by
the issues' own priority notes, with CI and default-worker runs green
throughout. Each PR was individually justified (flaky tests tax every
future session with a re-run and a baseline comparison, and #365's original
2026-09-04 evidence did record default-worker failures), and the work is
now plausibly *done*: the isolated classes are all fixed, and the Playwright
config documents how to tell environment load from a regression. But the
customer saw four PRs of value while the team spent six making its own
tests robust. If a next period looks the same — new flake classes appearing
at the same rate the old ones are fixed — the question to ask is no longer
"which pattern fixes this spec" but whether the real-time-recording export
architecture (wall-clock capture asserted by decoding) needs a structural
answer, because per-spec hardening would then be a treadmill. #377's two
uncaptured one-off shapes are the tail to watch.

**One session filled the WIP cap with three of its own PRs, concentrating
all review on the next session** — the concentration #370's deferral note
had warned about that same morning. The rules permit it (three is the cap,
and the issues were genuinely independent: disjoint files, verified at
review), and this time it was fine — small pattern-application diffs, all
three merged in one pass. But it put ~1,000 diff lines from a single author
in front of a single reviewer with no second perspective anywhere in the
set, on work where author and reviewer error modes correlate (all three
PRs' correctness turns on the same presented-frame reasoning). Recorded as
an observation, not a proposal: the case for a rule should wait for an
instance where it actually hurt.
