# Retrospective 2026-08-31

Scope: the ten PRs merged since the fifth retrospective (#162): #161, #165,
#184 (process, #173), #185, #186, #187, #200, #201, #202, #205.

Trigger: ten PRs merged since the last retrospective — double the "roughly
every five" cadence in `docs/rules/process-improvement.md`, for the third
period running. No failure pattern forced an earlier one.

Evidence reviewed: the merge commits on `main` since #162; all main-branch
workflow runs in the period (CI runs 141–160 and their Pages deploys, each
checked for its conclusion); the #200 review thread end to end; the #170/#172
feedback triage into #180/#181; the #182 approval and its derived batch
(#189–#195); the customer's #173 direction as implemented by #184; and the
narrow-viewport debugging evidence recorded in #208.

## Went well

**Main was green the entire period.** Every main-branch CI run and deploy in
the window concluded `success` — ten merges, zero broken-main incidents. At
period end the suite stands at 837 unit tests and 88 Playwright tests, all
passing.

**The author ≠ reviewer chain caught a real bug and stayed honest through
three sessions.** #200's independent review found an acceptance-criterion
violation (undo could resurrect an entry whose media had been removed — its
object URL already revoked), *proved* it with executed unit tests rather than
asserting it, and required changes. A second session pushed the fix and
explicitly declared itself co-author, barred from merging. A third session
reviewed only the fix commit, validated the merged tree locally, and merged.
Nobody rubber-stamped, nobody merged their own work, and each handoff comment
told the next session exactly what remained.

**Family-sized splitting kept a large feature reviewable.** #181 (~a dozen
transitions) shipped as #202 (wipes + pushes) and #205 (dips, iris,
cross-zoom), exactly the split the issue itself proposed. Each PR extended
the one shared spec rule with unit-asserted "existing types render
byte-identical" evidence, so the reviewer of each could reason locally; the
second landed the same day it was opened.

**The customer loop is fast and the #173 practice is operating.** #182's
batch approval turned into six scoped issues (#189–#195) with the approved
priority order the same day; #189 (undo/redo) was implemented, reviewed,
fixed, re-reviewed, and merged within hours. Suggestions now exist as capped
`idea` + `ai-generated` issues per #184, with one (#204) open for review.

## Went poorly

**The retro cadence is fiction — fourth period in a row.** "Roughly every
five merged PRs" has produced retros at ten, eight, fourteen, and now ten
PRs per period, with nothing evidently lost: main stayed green and the same
lessons would have been available at five. The rule as written just
generates a standing non-compliance note in every retro. Proposed change
below.

**A latent layout defect surfaced as an unrelated PR's e2e failure.** The
app has scrolled horizontally at viewports under ~900px for some time
(`fr` grid tracks floor at min-content; the media library's non-wrapping
clip row sets a ~540px floor — measured at 875px total on an 800px viewport
on current main). Nothing asserted this, so it was discovered only when
#206's one extra preview button pushed a `preview-zoom` screenshot probe
fully off the 800px test viewport and two specs failed. Filed as #208 with
measurements. Two durable lessons for sessions:

- *Layout min-content is shared state across features*, the CSS analog of
  the fifth retro's "shared prose" note: a button added in one panel can
  widen every panel. The narrow-viewport specs are currently the only
  guard, and they guard it by accident.
- *When a spec fails on your branch, re-run it on main before assuming your
  diff is the cause.* The #206 session did, which turned a plausible-looking
  wrong fix (tweaking probe math) into the right one (stop the row from
  inflating the page) plus a correctly scoped bug report.

## Changes proposed

- Right-size the retrospective cadence to observed reality (~every ten
  merged PRs, keeping "sooner on a recurring failure pattern") — `process`
  issue #209.
- #208 (narrow-viewport overflow) is engineering work, filed and prioritized
  through the normal backlog, not a process change.
