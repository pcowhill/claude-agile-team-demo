# Retrospective 2026-08-19

Scope: PRs #33–#53 — everything merged since the first retrospective (#31,
which covered #2–#25). Eleven PRs: seven implementation (#37, #45, #46, #48,
#49, #50, #53) and four process (#33, #44, #51, #52).

Trigger: seven implementation PRs merged since the last retrospective
(`docs/rules/process-improvement.md` suggests considering one after roughly
five), and that retrospective explicitly deferred two watch items to "the next
retrospective."

Evidence reviewed: the eleven squash commits on `main` since `6923f62`, the
review threads on #46, #48, #49, #50 and #53, issue #43's full comment history,
the outcomes of all 44 `ci.yml` runs (the 30 most recent inspected
individually), and the closed issues #38, #40, #41, #42, #43, #47.

## Went well

**All three changes the last retrospective proposed shipped — and each has now
been exercised, not merely merged.**

- #28 → #33 documented that GitHub refuses a formal `APPROVE` under the shared
  account. The last retrospective counted nine reviews rediscovering this in
  nine different phrasings. Since then, reviews cite `docs/rules/review.md` in
  a single clause (#46, #48, #49, #50) or simply state the verdict without
  mentioning GitHub's behavior at all (#53). The rediscovery cost is gone.
- #30 → #51 added the `origin` check for a harness-assigned branch before the
  first push. Exercised almost immediately, and by the exact case it was filed
  about: the session that implemented #43 found the prior claimant's branch
  `claude/go-ydf1t8` absent from `origin` with no PR referencing the issue,
  concluded that claim had been abandoned without a handoff, and re-claimed on
  its own verified-absent branch — reasoning recorded in #43. A latent, silent
  hazard became a routine, documented decision.
- #29 → #52 required acceptance criteria to be team-executable or explicitly
  marked customer-verifiable. #43's seven criteria were all executable by a
  session, so no proxy or customer-verifiable criterion was needed and nobody
  had to make the judgment call #29 was filed about.

**The transitions epic validated three-way decomposition under the one-PR WIP
limit.** Free-form customer feedback #38 became #41/#42/#43 and shipped in that
order as #49 (794 insertions), #50 (458) and #53 (618) — each independently
reviewed, each with its own e2e coverage, none needing a follow-up fix. The
decomposition earned its keep concretely: #49's clamp (at most two clips live
at any sequence time) is what made the two-element preview in #50 and the
two-element exporter in #53 tractable, and both later reviews say so. The
customer's request is now delivered end to end — model, preview, and export.

**CI has still never been red.** 44 `ci.yml` runs to date; the 30 most recent
are all `success` at `run_attempt` 1. No branch has needed a follow-up commit
to go green, and no run has been retried.

**The first flaky test was treated as a bug, on the first occasion it could
be.** It surfaced during #46's review, was filed as #47 rather than folded into
that PR, and #48 root-caused it — an auto-click fired from a passive
`useEffect`, asserted outside `act()` — and fixed the cause instead of polling
around it with `waitFor`. #48's reviewer ran the full suite five consecutive
times before merging. No coverage was deleted to get green.

**Review evidence keeps getting stronger.** #48's five repeat runs; #49's
reviewer re-deriving why the clamp was necessary rather than taking the PR's
word; #53's reviewer substituting `main`'s single-element exporter under the
new e2e spec and confirming both new tests fail against it (mid-overlap red
channel `0.006` against a `> 40` blend threshold) — mutation-testing the tests
instead of trusting a green suite.

## Went poorly

**Handoff latency has a multi-day tail.** #53 was opened 2026-08-14 00:43 UTC
and merged 2026-08-19 15:44 — 5 days 15 hours. Every other PR in this period
merged 3 to 20 minutes after opening. The last retrospective concluded that
latency "is entirely session cadence … nothing to fix inside the process," and
that remains true: no rule can make a session start. What is worth recording is
the size of the tail. A finished, green, independently-reviewable feature sat
undelivered to the customer for most of a week while the backlog was otherwise
empty, so reasoning about throughput should assume hours-to-days, not the
"4 minutes to 10.4 hours" the last retrospective observed.

## Watch items (no action proposed)

**Still zero changes-requested reviews.** The last retrospective flagged this
and asked to revisit it. Every review sampled in this period (#46, #48, #49,
#50, #53) was submitted as `COMMENTED` with a positive verdict; combined with
the last retrospective's ten, that is 0-for-15 sampled. Reviews demonstrably
dig, CI has never been red, and this period's reviews did surface real findings
and record them proportionately rather than inflating or dropping them — the
transition duration field's `max` not reflecting the flanking-transition clamp
(#49), the removal dialog not trapping Tab (#46), and a progress criterion
accepted as correct-by-construction because it had no executed test (#53). The
benign explanation still fits. But `review.md`'s changes-required path remains
entirely unexercised, so nothing yet demonstrates that a session will block a
PR that deserves blocking. Carried forward unchanged: what would settle it is a
genuinely bad PR, not a new rule.

## Changes proposed

**None.**

All three changes from the last retrospective landed and are working; the one
open watch item should stay a watch item; and the new observation — the latency
tail — has no available process remedy. Filing a `process` issue to make this
retrospective look productive would be exactly the artificial activity
`docs/rules/operating-model.md` prohibits.
